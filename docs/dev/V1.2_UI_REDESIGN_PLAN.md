# CoFinder V1.2 UI Redesign Plan (Static Prototype Phase)

Status: planning + high-fidelity mockup only. No production UI refactor in this phase.

## Round 1 mockup — why it failed (post-mortem)

The first V1.2 mockup pass was rejected because it **changed skin, not structure**. Concretely:

1. **Same skeleton as V1.1** — Still read as “two big content regions + chrome,” not a reorganized desktop shell.
2. **Two large tables + flat queue** — Dual panes remained **boxed tables** with a **full-width queue strip** underneath, like a web admin panel rather than Finder / ForkLift.
3. **Too many borders and card framing** — Heavy outlines and panel “cards” reinforced a web dashboard look instead of macOS-style **separators and depth through tone**.
4. **Missing native IA affordances** — No **Finder-like source list** (sidebar), no **unified titlebar + toolbar band**, no **breadcrumb / path strip** distinct from a single path field, no **inspector column**, no **queue as a utility drawer**.
5. **Detached state demos** — Loading / empty / error were shown as **separate demo tiles** instead of **states inside a real pane**, so they did not prove the layout works under real browsing.

**Round 2 mockup** introduced a **single new IA** (sidebar, title strip, toolbar over content, split panes, path strips, drawer queue, inspector) with page-local state toggles.

**Round 3** refined **one Finder + dual-pane baseline** (no A/B/C skins): stronger macOS-style chrome, location control, list density, global inspector, compact transfer drawer.

**Round 4 (current mockup)** pushes **Finder-first**: higher-contrast system-blue selection, tighter file list vs. slightly roomier sidebar, **per-pane inspector** (local / remote / active-follow / off from dev rail), **single-line transfer rows**, Finder-like title tabs + toolbar + recessed path track, no global inspector column.

## 1. Current UI — Main Pain Points

- **Monolithic shell**: Most chrome lives in `App.tsx` with long conditional branches; hard to evolve layout without risk.
- **Visual hierarchy**: Tab bar, pane chrome, path bar, table, and transfer queue compete at similar weight; active pane and “where am I working” could be clearer.
- **Density vs. readability**: Table and toolbar mix compact controls with wide path fields; professional dual-pane tools often separate “navigation chrome” from “content grid” more explicitly.
- **State communication**: Loading, empty, and error states exist but could use a more consistent pattern (banner vs. inline vs. pane body).
- **Modal family**: Rename (inline), delete confirm, Get Info, Site Manager share patterns but are not yet a unified “dialog system” in the visual language.
- **Transfer queue**: Global queue is correct functionally; visually it can feel appended rather than integrated with the dual-pane workspace.

## 2. V1.2 Redesign Goals

- **macOS-native professionalism**: Reads as a serious desktop utility—calm typography, predictable spacing, clear separation of chrome vs. content.
- **Stronger information architecture**: Obvious order: global (tabs) → workspace (dual panes) → path/context → listing → transfers.
- **Scalable layout**: Structure that can later split into components without rewriting IPC or services.
- **Consistent state UX**: Loading / empty / error / disconnected patterns that feel intentional, not accidental.
- **Respect existing behavior**: Keyboard selection, context menus, queue semantics, and security model stay as implemented until explicit V1.2 milestones say otherwise.

## 3. Non-Goals (Explicit)

- **No drag-and-drop transfer** in V1.2 UI plan scope unless a later milestone is approved.
- **No remote edit auto-sync** workflow.
- **No rewrite** of SFTP, rsync, profiles, `safeStorage`, transfer queue, or IPC contracts as part of UI redesign planning.
- **No copying** of third-party brand assets (icons, logos, marketing copy, or proprietary visuals). Inspiration only: layout tiering and “pro dual-pane” restraint.

## 4. Visual Style Principles

- **macOS app temperament**: System-adjacent neutrals, subtle separators, purposeful use of one accent (selection / focus), no noisy gradients by default.
- **Professional and restrained**: Prefer clarity over decoration; avoid “web dashboard” tropes unless Option C is chosen deliberately.
- **Reference posture (not ForkLift)**: Study **ForkLift-class** dual-pane tools for **information structure**—strong pane headers, readable path strip, obvious active side—without reusing its brand, iconography, wording, or assets.
- **Accessibility-minded**: Sufficient contrast for selection and focus; do not rely on color alone for state (icons or weight can reinforce).

## 5. Proposed Information Architecture

| Zone | Role |
|------|------|
| **App shell** | Title / version strip (optional), global actions (Site Manager, settings later). |
| **Tab bar** | Session tabs; clear active tab; add/close affordances. |
| **Workspace** | Two panes (local \| remote) with shared vertical rhythm. |
| **Pane header** | Pane label (Local / Remote), connection status chip (remote), primary actions (Upload/Download/Disconnect as applicable). |
| **Path bar** | Unified path field + optional breadcrumb or “go up” cluster; errors scoped to pane. |
| **File list** | Sortable columns; selection, hover, inline rename affordance; context menu anchor. |
| **Transfer queue** | Collapsible dock; serial task list; status chips; pin/clear. |
| **Modals / popovers** | Delete confirm, Get Info, Site Manager, future prefs—shared radius, shadow, and header pattern. |

## 6. Milestone Split (Suggested, for Later Implementation)

1. **M1 — Shell & tokens**: Extract layout shell + CSS variables; no behavior change.
2. **M2 — Pane chrome**: Path bar + toolbar + pane header; wire to existing handlers.
3. **M3 — File grid**: Table styling, selection/hover, column resize (optional), empty/loading/error templates.
4. **M4 — Queue integration**: Queue as docked panel with shared visual system.
5. **M5 — Dialog system**: Unify modal headers, spacing, and destructive styling.
6. **M6 — Polish & docs**: Motion (subtle), release notes, smoke updates.

Each milestone should ship behind review with `npm test` / `npm run build` / targeted smoke.
