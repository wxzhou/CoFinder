# CoFinder V1.2 Development Plan

**Status:** planning approved — execution waits for explicit milestone commands (`开发 M1`, `开发 M2`, …).

**Theme:** Finder-first UI redesign for CoFinder — ship the **warm Finder-first** visual and information architecture from the approved static mockup into the production app, while **reusing V1.1 business logic** (IPC, services, selection, queue, profiles, etc.).

**Visual / IA source of truth (approved mockup):**

- `src/renderer/mockups/V12UiMockup.tsx`
- `src/renderer/mockups/v12-mockup.css`
- `src/renderer/mockups/mockData.ts` (data shapes only; production uses real state)
- Planning context: `docs/dev/V1.2_UI_REDESIGN_PLAN.md`

**Baseline docs (read before any Mx work):**

- `docs/dev/PROJECT_CONTEXT.md`
- `docs/dev/ARCHITECTURE.md`
- `docs/dev/DEVELOPMENT_RULES.md`
- `docs/dev/V1.1_PLAN.md` (completed feature set; do not regress)

## V1.2 total goal

Progressively land the mockup’s **Finder-like** shell in the real app:

- Finder-like **sidebar**
- Finder-like **title / tab / toolbar** chrome
- **Dual-pane** local / remote workspace
- **Per-pane inspector** (not a detached global right column)
- **Compact transfer drawer** at the bottom of the workspace
- **Remote disconnected** state shows an **embedded Site Manager / quick connect** surface inside the remote pane (major product improvement)
- Preserve and **reuse** existing V1.1 capabilities end-to-end

**Product posture:** “Finder baseline temperament + ForkLift-class dual-pane and remote workflow.” If you mentally remove the remote pane and transfer drawer, the **local** area should read as close to a **Finder** workspace as practical; remote pane, drawer, and per-pane inspector extend that base naturally.

**This is not a rewrite of CoFinder.** V1.2 is primarily **UI shell, layout, visual system, remote pane state machine, and transfer drawer integration**, with **minimal glue** to existing commands and state.

## Global development principles (mandatory for all milestones)

### 1. Plan before code

- When the user says **`开发 Mx`**, the implementer must **first restate in the reply**: that milestone’s **goal, scope, non-goals, likely files, risks, and tests** (per sections below), then implement.
- If the current codebase structure **conflicts** with the milestone as written, **stop and explain the conflict** before a large refactor.

### 2. Strict scope control

- **M1:** only M1. Do not implement M2+ in the same change set.
- **M2:** only M2. Do not slip M3/M4 work into M2.
- Same discipline for M3–M6.

### 3. Preserve V1.1 business logic

Do **not** rewrite unless a milestone explicitly calls for a **small, justified** hook change:

- Local browsing (`LocalFileService`, `local:*` IPC)
- Remote SFTP browsing (`RemoteFileService`, `remote:*` IPC)
- Tab state isolation (renderer tab model in `App.tsx`)
- Profiles / Site Manager (`ProfileRepository`, `profiles:*`, modal flow)
- `safeStorage` credential handling
- rsync upload/download and **transfer queue state machine** (`TransferQueueService`, `transfer:*`, `transfer:onUpdate`)
- Multi-selection, Shift range, Cmd/Ctrl+A (`selection.ts`, pane state)
- Context menus, Quick Look, rename, delete, properties (existing handlers and UI flows)

### 4. UI vs business layering

- Prefer **new shell / layout / presentational components** that call **existing** handlers and IPC via `window.cofinder` / existing callbacks.
- **Do not** reimplement SFTP, rsync, profile persistence, or selection algorithms inside purely visual components.

### 5. Feature flag and default UI (through M5)

- **M1** must introduce a **development-safe switch** so V1.1 UI remains the default path, e.g.:
  - **Query flag:** `?ui=v12` (recommended; mirrors existing dev-only `?mockup=v12` pattern in `main.tsx`), and/or
  - **Environment variable** (e.g. `COFINDER_UI_V12=1`) for Electron dev URL in `src/main/main.ts`, and/or
  - An explicit **in-code feature flag** for packaged builds until M6.
- **Do not** make V1.2 shell the **only** or **default** UI until **M6** explicitly allows it.

### 6. Strong regression discipline (every milestone)

Each completed milestone must document in the PR / commit message or session summary:

- **Files changed** (high level)
- **Acceptance criteria** met vs deferred
- **Manual smoke** steps run (subset of `docs/smoke-test.md` relevant to the milestone)
- **Risk to V1.1** behavior (what could have broken)
- **Commands:** `npm test`, `npm run build`, and `npm run dev` startup where applicable

### 7. No unnecessary dependencies

- **No new UI framework** (stay React + existing Vite/CSS approach).
- **No heavy** icon/animation/CSS-in-JS stacks for V1.2.
- If a dependency is truly required, **propose alternatives first** and wait for product confirmation.

### 8. Cursor execution rule

When the user says **`开发 Mx`**, execution **must** follow **this document’s Mx section** only. If scope ambiguity exists, clarify before coding.

### M1 — App shell / Finder-first chrome / feature flag

**Status:** implemented (shell behind `?ui=v12` / `COFINDER_UI_V12=1` in dev; `?mockup=v12` remains dev-only mockup).

#### Goal

Upgrade the **page skeleton** from V1.1 to the V1.2 **Finder-first app shell** (sidebar, title/tab strip, toolbar, dual-pane **content area**, bottom **drawer region**), behind a **feature flag**, **without** rewriting pane internals or business logic.

#### Scope

1. Introduce a **new UI shell** in the renderer (new components and/or a thin `AppV12` wrapper — exact structure left to M1 implementation plan in-code).
2. Implement shell regions matching the mockup **structure** (not the mockup **dev rail**):
   - Title / tab strip (can wrap or replace visual role of current `TabBar` in v12 mode only)
   - Toolbar row (placeholders or wired to no-ops until M5 where noted)
   - Sidebar (structure + navigation placeholders; can mirror mockup sections before full data bind)
   - Main **workspace**: dual-pane **slots** (left / right)
   - Bottom **transfer drawer chrome** (collapsed/expanded **shell**; may show empty or “use v1.1 queue below” until M5)
3. **Feature flag** (at least one of):
   - `?ui=v12` on renderer URL (recommended)
   - and/or `COFINDER_UI_V12=1` (or similar) in dev to open `?ui=v12` from `main.ts`, analogous to `COFINDER_V12_MOCKUP`
   - Document chosen mechanism in `README.md` / smoke doc in M1 or M6 as appropriate
4. **V1.1 UI path unchanged** when flag is off: existing `App` layout and behavior.
5. **Extract or reuse** visual tokens from `v12-mockup.css` into maintainable production CSS (e.g. shared variables file or scoped module) — **do not** ship the mockup-only **dev rail** in production shell.

#### Non-goals

- No change to local/remote **file list** implementation beyond hosting existing subtree if needed for smoke (prefer **flag off** still runs old UI unchanged).
- No change to **selection** algorithms.
- No **Site Manager** redesign (modal may still open from menu/button as today).
- No **transfer queue data** logic changes.
- No **per-pane inspector** content (M3).
- No **embedded remote connect** (M4).
- **Do not** set v12 shell as **default** for all users (reserved for M6).

#### Likely files to change

- `src/renderer/main.tsx` (branch: `ui=v12` vs `mockup=v12` vs default `App` — design carefully to avoid mutually exclusive bugs)
- `src/renderer/App.tsx` (entry composition or extract shell parent)
- New: `src/renderer/shell/` or `src/renderer/v12/` (recommended folder for shell components + tokens)
- `src/renderer/styles.css` or new `src/renderer/v12/v12-shell.css` (production tokens)
- `src/main/main.ts` (optional dev URL query for `?ui=v12`)
- Tests under `tests/` if routing logic is non-trivial

#### Implementation notes

- Keep **`?mockup=v12`** behavior **dev-only** and **separate** from production shell flag (`?ui=v12`) to avoid mixing mock static state with real app.
- Prefer **composition**: `ui=v12` renders `<AppShellV12>{legacyPaneContentLater}</AppShellV12>` rather than duplicating entire `App`.
- **Electron `hiddenInset` / traffic lights** are out of scope for M1 unless already trivial; focus on **renderer** chrome first.

#### Regression risks

- Wrong `main.tsx` branch could render blank or double-mount React.
- Accidentally coupling shell to mockup build or breaking production `file://` load.

#### Tests

- Unit tests for URL/param parsing if extracted to a pure function.
- Existing Vitest suite must remain green.

#### Acceptance criteria

- With **`?ui=v12`** (or documented equivalent), user sees: **sidebar + toolbar + title/tab area + dual-pane region + bottom drawer region**.
- With flag **off**, app behaves as **V1.1** today.
- `npm test` passes; `npm run build` passes; `npm run dev` starts with and without flag.

#### Manual smoke test checklist (M1)

- [ ] Launch dev without v12 flag → full V1.1 UI, smoke critical path (open app, one local browse).
- [ ] Launch with v12 flag → new shell visible; can return to v1 by removing flag.
- [ ] Packaged build (optional in M1): flag off still loads classic UI (v12 path may be dev-only until M6 — document if so).

### M2 — Pane shell + local/remote list wiring

#### Goal

Mount **real** local and remote browsing UI inside the V1.2 **pane shell** so dual-pane file operations work under `?ui=v12` with minimal visual completion (no inspector yet).

#### Scope

1. **Pane-level shell** per side:
   - Pane title / context line (from tab + path state)
   - Meta / subtitle (local vs remote identity)
   - Path / location bar bound to existing `pathInput` / navigation behavior
   - **Existing** file table/list **moved or composed** into pane body (reuse current row rendering, context menu, double-click, etc.)
2. **Local pane:** wire existing local list + handlers into v12 local pane.
3. **Remote pane (connected):** wire existing remote list when `connectionStatus === "connected"`.
4. Preserve: list rendering, click/double-click, multi-select, Shift range, Cmd/Ctrl+A, context menu, refresh / enter directory, sort controls as they exist today (may relocate visually).
5. **Active vs inactive pane:** at least **basic** visual distinction (border, background tint, or focus ring) consistent with mockup direction.

#### Non-goals

- No **per-pane inspector** (M3).
- No **embedded Site Manager** in disconnected remote pane (M4).
- No full **loading / empty / error** visual redesign (use existing strings/components where possible; polish in M6).
- No **drag-and-drop** transfer.
- No rewrite of **selection.ts** or IPC.

#### Likely files to change

- `src/renderer/App.tsx` (split layout or pass props into shell)
- New pane shell components under `src/renderer/v12/` or `src/renderer/components/panes/`
- Possibly `src/renderer/components/TabBar.tsx` (only if tabs move into shell without breaking v1 path)

#### Implementation notes

- Prefer **lifting** existing table JSX into a child component **without** changing handler semantics.
- **Remote disconnected:** may still show current simple placeholder until M4, but pane chrome should exist.

#### Regression risks

- Event handlers lost during extract → selection or context menu breaks.
- Path input out of sync with `currentPath` after refactor.

#### Tests

- Renderer tests for selection helpers unchanged; add tests if new wrapper components contain branching.
- Manual: multi-select and context menu on both panes under `?ui=v12`.

#### Acceptance criteria

- Under `?ui=v12`: browse local directories; browse remote when connected; double-click enters directories.
- Multi-select, Shift range, Cmd/Ctrl+A, context menu behave as V1.1.
- Path/location reflects current directory.
- Active/inactive pane visually distinguishable.
- `npm test` / `npm run build` pass.

#### Manual smoke test checklist (M2)

- [ ] Local: navigate, select range, Cmd+A, open context menu, open folder.
- [ ] Remote: connect with profile, list, same selection/menu checks.
- [ ] Toggle focus between panes; selection state per pane preserved.
- [ ] Flag off: V1.1 path unchanged.

### M3 — Per-pane inspector

#### Goal

Implement **per-pane inspector** inside each pane (local inspector in local pane; remote in remote pane), fed by **current selection** and reusing existing actions (Quick Look, Reveal, Copy Path, etc.).

#### Scope

1. Inspector **component** per pane (right side of pane split), modes:
   - `off` — inspector hidden or minimal strip
   - `local` — always show local selection info in local pane
   - `remote` — always show remote selection info in remote pane
   - `active` (recommended) — inspector follows **focused** pane only; unfocused pane hides inspector or shows collapsed state (product decision in M3 kickoff — document chosen behavior)
2. Display for selected file/dir (when selection is single; for multi-selection show summary or first item — **document rule**):
   - Name, kind, size, mtime, path (local or remote), permissions when available from existing models / `PathInfo`
3. Wire **existing** actions only:
   - Quick Look (local rules; remote limitations per V1.1)
   - Reveal in Finder / remote equivalent if present
   - Copy Path / Copy Remote Path via `system:copyText` / existing helpers
4. **No global** right-column inspector that competes with dual-pane width.

#### Non-goals

- No rich preview (Quick Look remains system preview).
- No rewrite of **Get Info** modal / properties pipeline — inspector is **summary**; full Get Info can remain modal if today.
- No **embedded remote connect** (M4).
- No **transfer drawer** behavior changes beyond layout if already present (M5).

#### Likely files to change

- `src/renderer/App.tsx` (selection → inspector props)
- New: `src/renderer/v12/PaneInspector.tsx` (or similar)
- Reuse types from `src/shared/types/models.ts`, `PathInfo` usage patterns from existing Get Info flow

#### Implementation notes

- Inspector actions should match **mockup v5** posture: **secondary** (text-like), not primary CTA buttons, unless product overrides.
- Clear empty state when nothing selected.

#### Regression risks

- Stale selection when switching tabs or disconnecting remote.

#### Tests

- Unit tests for inspector formatting helpers (pure functions).
- Manual: change selection → inspector updates; Quick Look / copy path still work.

#### Acceptance criteria

- Local and remote inspectors render **inside** their panes only.
- Modes `off` / `local` / `remote` / `active` behave per M3 kickoff decision.
- Quick Look / Reveal / Copy Path **not regressed** under `?ui=v12`.
- `npm test` / `npm run build` pass.

#### Manual smoke test checklist (M3)

- [ ] Single file selection → inspector fields match list/Get Info data.
- [ ] Multi-select rule verified (documented behavior).
- [ ] Inspector off → full width to list.
- [ ] Tab switch → inspector clears or updates correctly.

### M4 — Remote state system + embedded Site Manager / quick connect

#### Goal

Complete the **remote pane** as a product-grade surface: **disconnected** shows **embedded** profile picker + quick connect + link to full Site Manager; **connecting / error / connected** have clear in-pane states; **connected** flows into existing remote list (M2).

#### Scope

1. Define explicit **remote pane UI states**: `connected` | `disconnected` | `connecting` | `error` | (optional `empty` if product wants empty remote home).
2. **Disconnected UI** inside remote pane:
   - Saved profiles / recents (data from existing `profiles:list` and tab memory)
   - Quick connect fields: host, port, username, auth summary (password vs key per current model), Connect
   - Button to open **full Site Manager** modal (existing component)
3. Reuse **existing** connect / disconnect IPC and validation; no new auth system.
4. **Loading** and **error** surfaces in-pane (reuse or slim down existing copy).
5. After successful connect, transition to **connected** remote list without leaving v12 shell.

#### Non-goals

- No rewrite of **ProfileRepository** or **safeStorage**.
- No new auth methods.
- No rsync / transfer semantics change.
- No full **Preferences** app.

#### Likely files to change

- `src/renderer/App.tsx` (remote pane region conditional rendering)
- `src/renderer/components/SiteManagerModal.tsx` (possibly extract **embeddable** fragment from modal body — careful refactor; prefer composition over duplicate forms)
- Possibly small shared **presentational** form components

#### Implementation notes

- **Embedding** may require extracting a “profile list + quick connect” sub-view from `SiteManagerModal` into a shared component used by modal and remote pane — scope tightly; avoid behavior drift between embedded and modal.
- Security: password fields and saved password behavior must match V1.1 rules.

#### Regression risks

- Embedded flow bypasses validation used by modal.
- Credential save checkbox semantics diverge.

#### Tests

- Tests for extracted pure helpers (profile sorting, form validation mirrors if any).
- Manual: connect from embedded; connect from modal; disconnect; error path.

#### Acceptance criteria

- Disconnected remote pane is **useful** (not only “Not connected” stub).
- User can pick profile or quick connect and reach remote list.
- Full Site Manager still works for CRUD.
- Failures show in-pane **error** state.
- `npm test` / `npm run build` pass.

#### Manual smoke test checklist (M4)

- [ ] Embedded connect with saved profile.
- [ ] Quick connect with new host; cancel; error host.
- [ ] Open full Site Manager; create profile; see it in embedded list.
- [ ] safeStorage on/off behavior unchanged.

### M5 — Transfer drawer + top actions wiring

#### Goal

Wire the **real transfer queue** into the v12 **bottom drawer** and align **toolbar** actions with existing command handlers (refresh, connect/disconnect, upload/download, inspector toggle, etc.).

#### Scope

1. **Drawer:** hidden/shown, summary bar, compact list — bound to `transfer:list` + `transfer:onUpdate` (existing pattern).
2. Show per-task: state (`running` / `pending` / `success` / `failed` / canceled if shown), progress **percent**, source → destination, speed/ETA **if already available** in task model; do not invent fields without main support.
3. **Toolbar:** map buttons to **existing** handlers (same IPC as today).
4. **Visual density:** single-line / compact rows per mockup; avoid “large card” queue.

#### Non-goals

- No **rewrite** of `TransferQueueService` or rsync spawn rules.
- No **drag-and-drop** queueing.
- No advanced filtering/search of transfers.
- No new pause/resume unless already in codebase.

#### Likely files to change

- `src/renderer/App.tsx` (queue subscription placement vs shell)
- New: `src/renderer/v12/TransferDrawer.tsx`
- Toolbar button handler wiring in shell component

#### Implementation notes

- Drawer summary should stay **low contrast** when idle; **running** row is the primary emphasis (align with mockup v5).

#### Regression risks

- Missing unsubscribe when switching ui flag or unmounting shell.
- Queue actions (cancel/clear) not reachable.

#### Tests

- Any pure formatting for drawer rows; existing queue tests remain authoritative in main.

#### Acceptance criteria

- Real uploads/downloads visible in v12 drawer; expand/collapse works.
- Toolbar triggers same behaviors as V1.1 for refresh / transfer / connect.
- `npm test` / `npm run build` pass.

#### Manual smoke test checklist (M5)

- [ ] Enqueue upload; see running progress; completion.
- [ ] Clear completed; cancel (if applicable).
- [ ] Toolbar disconnect leaves remote pane consistent with M4 states.

### M6 — Polish / regression hardening / docs / release

#### Goal

**No new features.** Polish, full regression, documentation, packaging, and **decision** on default UI vs feature flag.

#### Scope

1. **UI polish:** hover, active/inactive pane, inactive selection appearance, truncation, alignment across sidebar / toolbar / path / inspector / drawer; empty/loading/error polish.
2. **Regression pass** against V1.1 checklist items (local/remote/tabs/profiles/queue/selection/context/rename/delete/properties/Quick Look/reveal/copy path/packaging).
3. **Docs:** `README.md`, this file (`V1.2_PLAN.md` status), `docs/smoke-test.md`, `docs/release-checklist.md`, `CHANGELOG.md` as applicable.
4. **Version bump** if shipping.
5. **Packaging:** `npm run package` / `npm run dist` verification.

#### Non-goals

- No new interactions (e.g. DnD).
- No large layout restructure.
- No V1.3 scope.

#### Likely files to change

- Broad but shallow across `src/renderer/**`, docs, `package.json` version

#### Implementation notes

- **Default UI:** explicitly choose one:
  - **A)** `?ui=v12` becomes default in packaged app and v1.1 layout deprecated, or
  - **B)** v12 remains behind flag until a later release — **must be stated in M6 completion notes**.

#### Regression risks

- Last-minute global CSS changes affecting v1.1 path if both coexist.

#### Tests

- Full `npm test`; manual full smoke; optional E2E if added later (not required by this plan).

#### Acceptance criteria

- `npm test`, `npm run build`, `npm run package` or `npm run dist` pass.
- Smoke and release checklists updated.
- Default vs flag decision **documented**.

#### Manual smoke test checklist (M6)

- Full matrix from **M6 non-goals** inverse: run entire `docs/smoke-test.md` relevant sections on **v12 default or flagged build** as chosen.
