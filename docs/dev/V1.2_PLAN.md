## V1.2 total goal

Progressively land the mockup’s **Finder-like** shell in the real app:

- Finder-like **sidebar**
- Finder-like **title / tab / toolbar** chrome
- **Dual-pane** local / remote workspace
- **Per-pane inspector** (not a detached global right column)
- **Compact transfer drawer** at the bottom of the workspace
- **Remote disconnected** state shows an **embedded Site Manager / quick connect** surface inside the remote pane (major product improvement)
- Preserve and **reuse** existing V1.1 capabilities end-to-end

**Product posture:** “Finder baseline temperament + ForkLift-class dual-pane and remote workflow.” If you mentally remove the remote pane and transfer drawer, the **local** area should read as close to a **Finder** workspace as practical; remote pane, drawer, and per-pane inspector extend that base naturally.

**This is not a rewrite of CoFinder.** V1.2 is primarily **UI shell, layout, visual system, remote pane state machine, and transfer drawer integration**, with **minimal glue** to existing commands and state.

## Global development principles (mandatory for all milestones)

### 1. Plan before code

- When the user says **`开发 Mx`**, the implementer must **first restate in the reply**: that milestone’s **goal, scope, non-goals, likely files, risks, and tests** (per sections below), then implement.
- If the current codebase structure **conflicts** with the milestone as written, **stop and explain the conflict** before a large refactor.

### 2. Strict scope control

- **M1:** only M1. Do not implement M2+ in the same change set.
- **M2:** only M2. Do not slip M3/M4 work into M2.
- Same discipline for M3–M6.

### 3. Preserve V1.1 business logic

Do **not** rewrite unless a milestone explicitly calls for a **small, justified** hook change:

- Local browsing (`LocalFileService`, `local:*` IPC)
- Remote SFTP browsing (`RemoteFileService`, `remote:*` IPC)
- Tab state isolation (renderer tab model in `App.tsx`)
- Profiles / Site Manager (`ProfileRepository`, `profiles:*`, modal flow)
- `safeStorage` credential handling
- rsync upload/download and **transfer queue state machine** (`TransferQueueService`, `transfer:*`, `transfer:onUpdate`)
- Multi-selection, Shift range, Cmd/Ctrl+A (`selection.ts`, pane state)
- Context menus, Quick Look, rename, delete, properties (existing handlers and UI flows)

### 4. UI vs business layering

- Prefer **new shell / layout / presentational components** that call **existing** handlers and IPC via `window.cofinder` / existing callbacks.
- **Do not** reimplement SFTP, rsync, profile persistence, or selection algorithms inside purely visual components.

### 5. Feature flag and default UI

- **M1–M5** introduced an opt-in switch so V1.1 UI could remain default during rollout (`?ui=v12`, dev env helpers, etc.).
- **M6+ product default:** V1.2 shell is **default** in dev and packaged builds (`src/renderer/uiMode.ts`). **Legacy classic UI:** `?ui=v11`, `?legacy=1`, **`COFINDER_LEGACY_UI=1`** (Electron main), or **`VITE_COFINDER_LEGACY_UI=1`** at renderer build time. **`?mockup=v12`** stays **dev-only** (static mockup), separate from production shell routing.

### 6. Strong regression discipline (every milestone)

Each completed milestone must document in the PR / commit message or session summary:

- **Files changed** (high level)
- **Acceptance criteria** met vs deferred
- **Manual smoke** steps run (subset of `docs/smoke-test.md` relevant to the milestone)
- **Risk to V1.1** behavior (what could have broken)
- **Commands:** `npm test`, `npm run build`, and `npm run dev` startup where applicable

### 7. No unnecessary dependencies

- **No new UI framework** (stay React + existing Vite/CSS approach).
- **No heavy** icon/animation/CSS-in-JS stacks for V1.2.
- If a dependency is truly required, **propose alternatives first** and wait for product confirmation.

### 8. Cursor execution rule

When the user says **`开发 Mx`**, execution **must** follow **this document’s Mx section** only. If scope ambiguity exists, clarify before coding.

- Existing Vitest suite must remain green.

### M2.7 — V1.2 sidebar: local favorites + remote placeholder

**Status:** implemented (product scope **redefined** from the earlier “Finder sidebar / Sites / Connections” sketch).

#### Goal

Ship a **minimum viable** v12 sidebar: **persistent local favorites** (defaults + user-added paths), **local pane navigation only**, and a **non-interactive Remote Favorites placeholder** for V1.3. **No** Finder plist scraping, **no** sidebar-driven Site Manager / profile connect, **no** remote favorite navigation in V1.2.

#### Scope (V1.2)

1. **Local Favorites**
   - Defaults (resolved at runtime via Electron `app.getPath`): **Home**, **Desktop**, **Downloads**, **Documents** — never hard-coded usernames.
   - User can **add** the current local directory (`+` on the section header).
   - User can **remove** any row (including built-ins); removed defaults are stored as **`hiddenDefaultIds`** in the JSON. **Restore default locations** brings Home / Desktop / Downloads / Documents back (custom entries unchanged).
   - **Persistence:** `local-sidebar-favorites.json` under Electron **userData** (`custom[]` + optional `hiddenDefaultIds[]`; corrupt/missing file → safe defaults + empty custom).
   - **Click:** `navigateLocal` on the active tab, `setActivePane("local")`, clear local selection / v12 local inspector reveal timer; **does not** change remote path, disconnect, or queue.
   - **Active row:** `pickActiveFavoriteId` — normalized path equality or **longest-prefix** directory match on local `currentPath` only.
   - **Missing paths:** `fs.access` in main → `pathExists` flag; row still clickable (list error surfaces in pane if truly missing).
2. **Remote Favorites**
   - Static **disabled** placeholder (“Coming in V1.3”); **no** IPC, **no** profiles list, **no** navigation.
3. **IPC:** `localFavorites:list` | `add` | `remove` | `resetDefaults` with `{ ok, data }` / `{ ok, error }`; validation in main (`validateLocalPathInput`, duplicate detection).

#### Non-goals (V1.2)

- No reading **Finder sidebar** private configuration.
- No **remote favorites** implementation, no sidebar **→** Site Manager / connect.
- No changes to SFTP, **safeStorage**, rsync, transfer queue, or selection algorithms.

### M3 — Per-pane inspector

**Status:** implemented (`?ui=v12`: per-pane `V12PaneInspector` in `v12m-pane-split` **only when that pane has a selection**; no global right column).

#### Goal

Implement **per-pane inspector** inside each pane (local inspector in local pane; remote in remote pane), fed by **current selection** and reusing existing actions (Quick Look, Reveal, Copy Path, etc.).

#### Scope

1. Inspector **component** per pane (right side of pane split). **Visibility:** the column is **hidden** with empty selection. Row **`click` with `detail === 1`** starts a **short timer (~350ms)** before showing the inspector **only while the column is hidden** (no hide-then-show flash when switching rows with the inspector already open). **`detail >= 2`** cancels that timer and keeps the column hidden so **double-click to enter a folder** rarely mounts the column. **Cmd/Ctrl+A** and **tab switch** still show the inspector immediately when there is a selection. Remote pane requires **connected** state when selected.
2. **Multi-selection (≥2):** inspector shows **count**, **sum of file sizes** (directories excluded from the sum), **preview of up to four names**, and a short note that per-field details apply to a single item. **Get Info**, **Quick Look**, and **Reveal** are **disabled** in the inspector for multi-select (same constraint as the existing Get Info modal); **Copy path(s)** remains available.
3. Display for selected file/dir (when selection is single; for multi-selection show summary or first item — **document rule**):
   - Name, kind, size, mtime, path (local or remote), permissions when available from existing models / `PathInfo`
4. Wire **existing** actions only:
   - Quick Look (local rules; remote limitations per V1.1)
   - Reveal in Finder / remote equivalent if present
   - Copy Path / Copy Remote Path via `system:copyText` / existing helpers
5. **No global** right-column inspector that competes with dual-pane width.

#### Non-goals

- No rich preview (Quick Look remains system preview).
- No rewrite of **Get Info** modal / properties pipeline — inspector is **summary**; full Get Info can remain modal if today.
- No **embedded remote connect** (M4).
- No **transfer drawer** behavior changes beyond layout if already present (M5).

#### Likely files to change

- `src/renderer/App.tsx` (selection → inspector props)
- `src/renderer/v12/V12PaneInspector.tsx`, `v12InspectorVisibility.ts`, `v12InspectorSummary.ts`
- Reuse types from `src/shared/types/models.ts`, `PathInfo` usage patterns from existing Get Info flow

#### Implementation notes

- Inspector actions should match **mockup v5** posture: **secondary** (text-like), not primary CTA buttons, unless product overrides.
- Clear empty state when nothing selected.

#### Regression risks

- Stale selection when switching tabs or disconnecting remote.

#### Tests

- Unit tests for inspector formatting helpers (pure functions).
- Manual: change selection → inspector updates; Quick Look / copy path still work.

#### Acceptance criteria

- Local and remote inspectors render **inside** their panes only.
- Inspector column **hidden** with empty selection; **shown** when that pane has a selection (remote only when connected).
- Quick Look / Reveal / Copy Path **not regressed** under `?ui=v12`.
- `npm test` / `npm run build` pass.

#### Manual smoke test checklist (M3)

- [ ] Single file selection → inspector fields match list/Get Info data.
- [ ] Multi-select rule verified (documented behavior).
- [ ] Clear selection (e.g. click list background) → inspector column hides; list full width.
- [ ] Tab switch → inspector clears or updates correctly.

### M5 — Transfer drawer + top actions wiring

**Status:** implemented (`V12TransferDrawer` + compact rows bound to existing `transferTasks` / `transfer:onUpdate`; `V12Toolbar` wired from `App.tsx`. **Connect:** single plug — opens Site Manager when disconnected, **Disconnect** when connected. **New folder** remains disabled — no underlying mkdir flow in V1.1. **Search / Columns** non-interactive per pre-M5 rule.)

#### Goal

Wire the **real transfer queue** into the v12 **bottom drawer** and align **toolbar** actions with existing command handlers (refresh, connect/disconnect, upload/download, inspector toggle, etc.).

#### Scope

1. **Drawer:** hidden/shown, summary bar, compact list — bound to `transfer:list` + `transfer:onUpdate` (existing pattern).
2. Show per-task: state (`running` / `pending` / `success` / `failed` / canceled if shown), progress **percent**, source → destination, speed/ETA **if already available** in task model; do not invent fields without main support.
3. **Toolbar — action wiring (explicit checklist):** each control maps to **existing** V1.1 behavior (same IPC / handlers as classic UI):
   - **Back / forward / up** — history navigation for the **focused** pane (local vs remote rules unchanged).
   - **Refresh** — reload current directory for the focused pane.
   - **Connect** — when remote disconnected: open connect surface (M4 embedded or modal per product choice); when connected: no-op or contextual **disconnect** if a single control toggles (document chosen pattern).
   - **Disconnect** — when remote connected (may be toolbar or pane chrome; must not regress).
   - **Upload / download** — existing enqueue paths with current selection and connection guards.
   - **New folder / delete** — existing flows including confirmations.
   - **Inspector toggle** — show/hide or mode cycle for **M3** per-pane inspector (meaningful once M3 exists; if M5 lands before M3, stub or omit until inspector ships).
   - **Quick Look / Get Info** — wire only if the toolbar exposes them in the final design; otherwise keep primary entry via **context menu** and inspector.
   - **View mode** (list vs columns, if present) — defer or map to supported view only; do not advertise unsupported modes as live.
4. **Pre-M5 UX rule (M2–M4):** any toolbar control that is **not** yet wired **must** be **`disabled`** *or* **visually and semantically non-interactive** (e.g. `pointer-events: none`, `aria-disabled="true"`, `tabIndex={-1}`) — **never** a normal, focusable, “enabled-looking” control that **no-ops** on click (misleading and fails QA).
5. **Visual density:** single-line / compact rows per mockup; avoid “large card” queue.

#### Non-goals

- No **rewrite** of `TransferQueueService` or rsync spawn rules.
- No **drag-and-drop** queueing.
- No advanced filtering/search of transfers.
- No new pause/resume unless already in codebase.

#### Likely files to change

- `src/renderer/App.tsx` (queue subscription placement vs shell)
- `src/renderer/v12/V12TransferDrawer.tsx`, `src/renderer/v12/V12Toolbar.tsx`, `src/renderer/v12/v12TransferRowSummary.ts`
- Toolbar passed into `AppShellV12` from `App.tsx`

#### Implementation notes

- Drawer summary should stay **low contrast** when idle; **running** row is the primary emphasis (align with mockup v5).
- Toolbar wiring should live next to **`AppShellV12`** / a thin **`V12Toolbar`** container that receives callbacks from **`App.tsx`**, mirroring how classic toolbar buttons obtain scope (active tab, active pane, selection).

#### Regression risks

- Missing unsubscribe when switching ui flag or unmounting shell.
- Queue actions (cancel/clear) not reachable.

#### Tests

- Any pure formatting for drawer rows; existing queue tests remain authoritative in main.

#### Acceptance criteria

- Real uploads/downloads visible in v12 drawer; expand/collapse works.
- Toolbar triggers same behaviors as V1.1 for refresh / transfer / connect.
- `npm test` / `npm run build` pass.

#### Manual smoke test checklist (M5)

- [ ] Enqueue upload; see running progress; completion.
- [ ] Clear completed; cancel (if applicable).

## V1.3 — Sidebar: per-profile remote favorites (planned only)

**Not part of V1.2.** Captures product intent for sidebar **remote** shortcuts after V1.2 ships.

1. **Model:** extend `ServerProfile` (or adjacent profile metadata) with `remoteFavorites: string[]` — POSIX-normalized absolute remote paths, **no secrets** in this array.
2. **When connected:** if the active connection was opened from a saved profile, show that profile’s `remoteFavorites` in the sidebar (replacing the V1.2 placeholder section).
3. **Interactions:** click row → `listRemotePath` / existing remote navigation on **remote pane** only; add “current remote path” to the **active profile’s** list; remove one path from profile; persist via **ProfileRepository** (or a small sidecar file keyed by `profileId`).
4. **Edge cases:** profile deleted → drop cached favorites UI; host/username change does not auto-mutate paths; missing path → same class of errors as today’s remote list; permission errors surfaced without leaking credentials.
5. **Out of scope for this note:** exact UI copy, caps on list length, import/export.
