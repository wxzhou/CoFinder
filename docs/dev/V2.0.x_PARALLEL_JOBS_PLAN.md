# CoFinder V2.0.x Parallel Jobs Plan

## Status

Planned for a future V2.0.x release. Do not implement as part of v1.8.9 unless this plan is explicitly activated.

## Decision

CoFinder should not move from the current global serial Jobs queue to unrestricted parallel execution. The intended model is a **multi-lane job scheduler**:

- **Transfer lane:** upload and download share one serial lane. Default concurrency: `1`.
- **Compression lane:** gzip jobs run in their own lane. Default concurrency: `2`; configurable range: `1-4`.
- **Delete lane:** local and remote delete remain serial. Default concurrency: `1`; do not expose a parallel delete setting in the first implementation.
- **Future remote mutation lane:** remote copy/move can either use a new lane or join the delete lane after its path-conflict semantics are designed.

The primary user need is to keep remote gzip work from blocking upload/download and to allow a small number of independent gzip jobs to run together. Upload/download parallelism is not a priority because total bandwidth is usually the bottleneck. Delete parallelism is not a priority because server I/O is usually the bottleneck and path conflicts are riskier.

## Required Path Locks

The scheduler must reject or hold overlapping work before starting a job:

- The same file cannot have two gzip jobs running or queued.
- A file cannot be gziped while its parent directory is being deleted.
- A directory cannot be deleted while a child upload/download/gzip/delete job is running or queued.
- A transfer cannot write to a destination that is under a running delete.
- A delete cannot remove a source/destination path used by a running transfer.
- Remote locks must include `connectionId` or stable profile/session identity; local locks use absolute local paths.

Conservative behavior is preferred: if overlap is ambiguous, keep the later job pending or fail early with a clear message.

## Scheduler Shape

Replace the single `running: RunningContext | null` state in `TransferQueueService` with:

- `running: Map<string, RunningContext>` keyed by task id.
- a lane resolver such as `laneForTask(task): "transfer" | "gzip" | "delete"`.
- lane concurrency settings, initially `{ transfer: 1, gzip: settings.transfer.gzipConcurrency, delete: 1 }`.
- a pump that repeatedly starts the oldest pending job whose lane has capacity and whose path locks are available.

The Jobs pane remains unified: all lanes appear in one list and keep the existing All / Running / Failed / Done filters. Running counts may be greater than one after this milestone.

## Preferences

Add a Jobs preference:

- **Gzip concurrency**
  - Type: numeric stepper/input.
  - Default: `2`.
  - Range: `1-4`.
  - Applies to subsequently started jobs; running jobs are not interrupted when the value changes.

Do not expose upload/download or delete concurrency in the first version.

## Stop, Cancel, Retry

- Cancel remains allowed only for pending jobs.
- Stop must address the specific running task id and only stop that task.
- Retry failed should enqueue failed jobs back into their original lanes and honor current locks/concurrency.
- App shutdown must stop all running child processes and mark all running jobs as stopped.

## Tests

Add unit tests for:

- gzip jobs can run in parallel up to configured concurrency.
- upload/download remain serial.
- delete remains serial.
- transfer and gzip can run at the same time.
- parent/child path conflicts prevent unsafe starts.
- retry-all does not exceed lane limits.
- shutdown stops all running jobs.
